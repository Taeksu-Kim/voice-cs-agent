## 2. 원칙

1. **정의·실행·정책을 분리한다.** 정의는 카탈로그(도구 서버), 실행은 도메인 API, 정책은 에이전트가 맡는다.
2. **일반화하는 것은 도구 호출이지 에이전트가 아니다.** 업무 절차(인증 → 재확인 → 실행 등)와 게이트는 에이전트의 도메인 로직으로 남는다.
3. **업무 규칙은 도메인 API에만 둔다.** 에이전트는 형식·정책·근거만 검증하고, 업무 규칙을 복제하지 않는다.
4. **위험도와 실행 조건은 승인된 값만 쓴다.** 도구 소유 팀이 단독으로 바꾸지 않는다.
5. **고객 식별자는 컨텍스트에서 주입한다.** 모델이 인자로 고객을 지정하지 못하게 한다.
6. **데모는 얇게 한다.** 경계는 지키되 각 층의 구현은 단순하게 간다.

## 3. 구성 요소

| 구성 요소 | 책임 | 하지 않는 것 |
|---|---|---|
| **에이전트 서버** | 워커 정책, 턴 상태, 게이트, 형식·근거 검증, 대화 흐름, 컨텍스트 주입, 통화 제어 도구 | 업무 규칙 검증, 업무 데이터 저장 |
| **도구 서버 (MCP)** | 카탈로그 로드·검사, `tools/list`·`tools/call`, 이름→도메인 API 라우팅, 호출 로그 | 업무 검증, 대화 흐름, 응답 가공 |
| **도메인 API** | 받은 파라미터로 사실·업무 규칙 검증, 업무 데이터 접근, 결과 반환 | 위험도 판단(카탈로그 값을 따름), 대화 상태, 세션 조회 |

의존성은 **에이전트 → 도구 서버 → 도메인 API** 한 방향이고, 배포는 셋 다 독립이다.

**근거**
- 도구를 소유하는 쪽과 에이전트의 배포를 분리한다. 도구 정의나 파라미터가 바뀌어도 에이전트 코드를 고치지 않는다.
- 도구 서버와 도메인 API는 실서비스에서 소유 팀이 다르다(도구 서버 = 플랫폼, 도메인 API = 각 업무 팀). 데모에서도 프로세스를 나눠 이 경계를 실행 단위로 보이게 한다.
- 도구 서버는 AI 에이전트가 도구를 발견하고 호출하는 계층이다. HTTP로 직접 만들면 MCP가 정한 도구 목록·호출 형식을 다시 만들게 되므로 표준(MCP)을 쓴다.

**프로세스 (데모)**

| 프로세스 | 역할 |
|---|---|
| 에이전트 + 웹 (8080) | 기존 FastAPI 앱 |
| 도구 서버 (MCP, 8021 `/mcp`) | 신규 — `scripts/run_tools.py` |
| 도메인 API (FastAPI, 8020) | 신규 — `scripts/run_tools.py` (평가·개발 모드, `/_fixtures` 켬) |
| LLM·임베딩·리랭커·음성 | 기존 모델 서버 |

## 4. 카탈로그

### 4-1. 관리와 리로드

- **관리**: MCP 서버가 `catalog/<서비스>.yaml`을 읽는다. 파일은 5-1의 서비스(경로) 단위로 나눠, 서비스 팀이 자기 파일을 소유하는 구조로 둔다. 별도 카탈로그 서비스는 두지 않는다.
- **제공**: 에이전트는 MCP `tools/list`로만 카탈로그를 받는다. YAML을 직접 읽지 않는다.
- **리로드 (두 단계)**
  1. MCP 서버: YAML을 다시 읽는 리로드 API (읽을 때 1차 검사, 4-3)
  2. 에이전트: `tools/list`를 다시 받는 리로드 API — 받은 뒤 2차 검사, 워커 허용 목록과 다시 교차. 워커가 허용한 도구가 목록에 없으면 경고
- **진행 중인 통화에는 적용하지 않는다.** 통화 시작 시 도구 목록을 스냅샷으로 잡고, 리로드는 새 통화부터 반영한다. 평가 실행도 한 실행 안에서 목록이 바뀌지 않는다.
- MCP 표준의 목록 변경 알림(`notifications/tools/list_changed`)은 쓰지 않는다. 명시적 리로드가 동작 확인과 평가 재현에 쉽다.

### 4-2. 항목 스키마

```yaml
# catalog/card.yaml
- name: suspend_card
  version: 1
  owner: card
  status: active                       # active | deprecated
  description: 고객 카드를 일시정지한다. 인증과 재확인 후에만 호출한다.
  endpoint: /card/suspend
  params:
    customer_id: {type: string, source: context}
    card_id:     {type: string, source: model, required: true,
                  description: lookup_cards 결과의 card_id,
                  grounded_by: lookup_cards.cards.card_id}
  risk: execute
  requires_auth: true
  requires_confirmation: true
  requires_contact: false
  asks_customer: false
  target_keys: [card_id]
  approved_by: platform
```

**파라미터 출처**
- `source: model` — `inputSchema`에 들어가 모델이 채운다. **파라미터 호출 평가의 대상**이다.
- `source: context` — `inputSchema`에서 빠진다. 에이전트가 통화 컨텍스트에서 채운다. 모델이 다른 고객을 지정할 수 없다.
- `grounded_by` — 근거 검증 규칙(7-2). 이번 통화에서 해당 도구 결과에 나온 값만 허용한다.

**효과 선언 (`effects`)**: 도구 결과가 에이전트의 대화 상태를 바꿔야 할 때 선언한다. 에이전트는 효과 이름만 알고 도구 이름은 모른다.
- `authenticate` — 결과가 `status: success`면 인증 상태를 켜고, 아니면 인증 실패 횟수를 올린다 (`request_app_auth`)

**필드 소유**

| 필드 | 누가 정하나 | 이유 |
|---|---|---|
| `name`, `description`, `params`, `endpoint`, `owner` | 팀 | 자기 API의 계약 |
| `risk`, `requires_*`, `asks_customer`, `target_keys` | **승인 필요** | 안전 규칙 |
| `version`, `status` | 팀 제안, 승인 확인 | 호환성과 폐기 관리 |

위험도 값: `read`(조회), `notify`(링크·예약·기록), `execute`(되돌리기 어려운 실행), `handoff`(이관·종료).

**파라미터 추가 시**
- 선택 파라미터 추가는 카탈로그만 고치면 에이전트 코드 변경 없이 반영된다.
- 필수 파라미터 추가는 호환을 깨므로 새 버전으로 낸다.
- 모델이 그 파라미터를 올바르게 쓰는지는 별개다. 워커 프로토콜에 사용법이 있으면 지시문 수정과 평가가 필요하다.

### 4-3. `tools/list`로 나가는 형태 (위험도 메타데이터)

```json
{
  "name": "suspend_card",
  "description": "고객 카드를 일시정지한다. 인증과 재확인 후에만 호출한다.",
  "inputSchema": {"type": "object", "properties": {"card_id": {"type": "string", "description": "lookup_cards 결과의 card_id"}}, "required": ["card_id"]},
  "annotations": {"readOnlyHint": false, "destructiveHint": true},
  "_meta": {
    "csagent/risk": "execute",
    "csagent/requires_auth": true,
    "csagent/requires_confirmation": true,
    "csagent/requires_contact": false,
    "csagent/asks_customer": false,
    "csagent/target_keys": ["card_id"],
    "csagent/context_params": ["customer_id"],
    "csagent/grounded_by": {"card_id": "lookup_cards.cards.card_id"},
    "csagent/effects": [],
    "csagent/version": 1
  }
}
```

1. **게이트는 `_meta`의 `csagent/*` 값만 읽는다.**
2. **표준 `annotations`도 채운다** (`read` → `readOnlyHint: true`, `execute` → `destructiveHint: true`). 다른 MCP 클라이언트와 의미를 맞추기 위한 것이고, 표준상 힌트라 **게이트 판단에는 쓰지 않는다.**
3. **메타데이터가 없거나 형식이 틀린 도구는 워커에 노출하지 않는다 (fail closed).** 에이전트 리로드 때 경고를 남기고 제외한다.
4. **검사는 두 번 한다.** MCP 서버가 YAML을 읽을 때 1차(허용된 `risk` 값, 필수 필드), 에이전트가 `tools/list`를 받을 때 2차. 에이전트 검사는 서버를 믿지 않는 마지막 방어선이다.
5. **SDK 확인 (2026-10-18, `mcp` 2.3.0)**: `types.Tool`에 `meta`(별칭 `_meta`)·`annotations`, `types.CallToolRequestParams`에 `meta`(별칭 `_meta`)가 있다. 저수준 `mcp.server.lowlevel.Server(on_list_tools=…, on_call_tool=…)`로 카탈로그를 직접 읽어 `_meta`까지 채운 목록을 돌려줄 수 있고, 전송은 `streamable_http_app`을 쓴다.

## 5. 도메인 API

### 5-1. 경로 구성

| 경로 | 서비스 | 도구 |
|---|---|---|
| `/shopping/*` | 쇼핑 주문 | lookup_orders |
| `/transfer/*` | 송금 | lookup_transfers |
| `/card/*` | 카드 | lookup_cards · suspend_card · report_card_lost |
| `/seller/*` | 셀러 계정·상태 | lookup_seller (O1·O2 공용) |
| `/ads/*` | 광고 영업 | record_lead (O2, 2단계) |
| `/auth/*` | 고객 인증 | request_app_auth |
| `/notify/*` | 알림·예약 | send_app_link · schedule_callback |
| `/_fixtures` | 평가·개발 전용 | 픽스처 심기·지우기 (9절) |

경로는 **소유 기준**으로 나눈다. `record_lead`는 셀러 정보가 아니라 광고 영업 파이프라인의 데이터라 `/ads`로 분리한다.

### 5-2. 무상태와 상태 소유

| 상태 | 소유 | 예 |
|---|---|---|
| **턴·대화 상태** | 에이전트 | 대화 기록, 현재 업무·단계, 확인 질문 등록, `executed_turn`, 이번 통화의 도구 호출 결과(trace — 근거 검증에 씀), 도구 목록 스냅샷 |
| **업무 데이터와 그 변경** | 도메인 API | 주문·카드·송금·셀러 목업 데이터, 실행 결과 반영(카드 정지 후 재조회하면 정지 상태) |

- 도메인 API는 **요청 처리에서 무상태**다. 세션 조회나 추가 조회 없이 받은 파라미터로만 처리한다.
- 다만 **목업 데이터 저장소는 `customer_id` 기준으로 변경을 기억**한다 — 지금 `mock.py`의 「정지 후 재조회 시 정지 상태」 동작을 유지하기 위해서다.
- 에이전트는 업무 데이터를 캐시해 판단에 쓰지 않는다. 필요하면 조회 도구를 다시 부른다. 근거 검증만 trace를 쓴다.

### 5-3. 응답 형식

```json
{"ok": true, "data": {...}}
{"ok": false, "error": {"code": "CARD_ALREADY_SUSPENDED", "message": "..."}}
```

오류는 **구조화된 코드**로 돌려준다 (`ORDER_NOT_FOUND`, `CARD_NOT_FOUND`, `CARD_ALREADY_SUSPENDED` 등). 에이전트는 코드를 대화로 바꿔 대응한다.

## 6. 호출 흐름

1. **통화 시작**: 통화 시작 처리(웹 서버, 평가 러너)가 고객을 정해 에이전트 컨텍스트에 둔다(실서비스의 콜 인프라·CTI 역할). 에이전트는 도구 목록을 스냅샷으로 잡는다.
2. **모델이 도구 호출**
3. **에이전트 검증**: 워커 허용 여부 → 근거 → 정책(게이트) → 형식 순 (7-2). 실패하면 실행하지 않고 모델에게 되돌린다.
   - 워커가 쓸 수 없는 도구면 근거 검증을 건너뛰고 게이트가 `not_allowed`로 막는다 — 근거 검증의 「먼저 조회하라」 피드백이 그 워커에 없는 조회 도구 쪽으로 모델을 이끌지 않게 (`loop.py` `_run_tool`)
   - 형식 검증(필수·허용값·모르는 인자)은 실행 직전 `registry.run`에서 한다 (기존 위치)
4. **`tools/call`**: 모델이 고른 업무 인자에, 에이전트가 컨텍스트 파라미터(`customer_id`)를 `_meta`의 `csagent/context`로 붙여 보낸다.
5. **도구 서버**: 이름으로 엔드포인트를 찾고, 업무 인자와 컨텍스트 파라미터를 합쳐 도메인 API에 전달한다.
6. **도메인 API**: 사실·업무 규칙 검증과 데이터 접근 후 5-3 형식으로 응답한다.
7. **에이전트**: 결과를 턴 상태에 반영한다 (예: 실행 성공 시 `executed_turn`).

### 6-1. 통화 제어 도구 — 에이전트 내장

`transfer_to_agent`, `end_call`, `ask_contact`는 업무 데이터가 아니라 **통화 자체를 제어**한다. 도메인 API가 아니라 에이전트(실서비스에서는 콜 인프라 연동) 쪽에 둔다. 이 도구들은 MCP를 거치지 않고, 모델에게는 MCP 도구와 같은 목록 형식으로 합쳐서 보여 준다. 게이트 메타데이터(`risk: handoff` 등)는 에이전트 코드에 둔다.

## 7. 인증과 검증

인증(누구인가)과 검증(이 요청이 올바른가)은 다른 문제다.

### 7-1. 인증 — 데모에서는 구조만

| 층 | 확인하는 것 | 데모 |
|---|---|---|
| 에이전트 → 도구 서버 | 호출자가 신뢰된 에이전트인가 | 생략 |
| 도구 서버 → 도메인 API | 도구 서버가 신뢰된 서비스인가 | 생략 |
| 도메인 API | 고객 인증이 `requires_auth`를 충족하는가 | 생략 — 자리만 두고 항상 통과 |

- **인증 도구 결과는 지금처럼 시나리오가 정한다.** `request_app_auth`의 성공·실패는 시나리오 픽스처 값을 그대로 돌려준다 — 인증 실패 시나리오(auth_fail 등)는 유지된다.
- **인증 전 실행 금지는 에이전트 게이트가 코드로 막는다.** 지시문이 아니라 게이트이므로 평가는 유효하다.
- **데모의 한계**: 실서비스에서는 도메인 API가 인증 토큰을 검증해 이중으로 막는다. 데모에는 이 두 번째 방어선이 없다. 에이전트 게이트의 `requires_auth`는 대화 흐름 가드이지 보안 경계가 아니다.
- 실서비스 구조: 인증 서버가 고객 ID·만료에 서명한 토큰을 발급 → 에이전트는 내용 모른 채 전달 → 도메인 API가 서명·고객 일치 검증.

### 7-2. 검증 계층

같은 검증을 두 번 하는 것이 아니라, **각자 볼 수 있는 것을 검증한다.**

| 검증 | 어디서 | 이유 |
|---|---|---|
| **형식** — 타입, 필수 인자, 허용값 | 에이전트 (도메인 API도 기본 검사) | `inputSchema`만으로 범용 처리. 모델에게 바로 되돌려 다시 부르게 한다. 지금 `registry.run`의 `bad_args`·`bad_value` 검사가 이 자리 |
| **근거** — 인자가 이번 통화의 대화·조회 결과에서 나온 값인가 | 에이전트 | 모델이 값을 지어냈는지는 도메인 API가 알 수 없다. 카탈로그 `grounded_by`로 범용 처리 |
| **정책** — 인증 전 실행 금지, 재확인, 중복 실행 | 에이전트 | 대화 상태를 아는 쪽만 판단할 수 있다. 지금의 게이트 |
| **사실·업무 규칙** — 대상이 있는가, 상태 전이가 가능한가, 기한 내인가 | 도메인 API (최종) | 데이터의 주인이고, 다른 호출처도 있다 |

**검증 실패 분류 (trace·평가)**

| 분류 | 단계 | 의미 |
|---|---|---|
| `invalid_args` | 에이전트 형식 검증 | 모델의 파라미터 형식 실수 |
| `ungrounded_args` | 에이전트 근거 검증 | 모델이 대화·조회에 없는 값을 씀 |
| `blocked` (기존) | 에이전트 정책 게이트 | 인증·재확인 등 절차 위반 시도 |
| `domain_rejected` | 도메인 API | 정상적인 업무 거부 (모델 실수가 아닐 수 있음) |

이 구분으로 **모델의 파라미터 호출 실수**와 **정상적인 업무 거부**를 따로 센다.

## 8. 장애·지연 처리

- **실패 결과 형태를 지금과 같게 유지한다.** 지금 `registry.run`(`registry.py:87-90`)은 백엔드 예외를 `TimeoutError: ...` 같은 실패 결과로 바꿔 모델에게 보여 준다. MCP 어댑터도 시간 초과·연결 실패를 같은 형태로 돌려준다 → `tool_failures` 장애 시나리오(예: `s5_card_loss`의 `report_card_lost: timeout`)가 그대로 동작한다.
- **타임아웃은 도구 호출당 3초로 시작한다.** 음성 지연 예산 기준의 출발값이고 측정값이 아니다. 홉 지연 실측 후 조정한다.
- **기동 헬스체크**: 에이전트 시작 시 `tools/list`를 받지 못하면 평가 실행은 시작하지 않고 실패로 끝낸다(도구 없이 돌면 결과가 전부 오염된다). 웹 데모는 오류를 화면에 표시한다.
- **홉별 지연 기록**: trace에 에이전트→MCP 전체 시간과 MCP→도메인 API 시간을 따로 남긴다. 기준선과 비교할 때 늘어난 지연이 어느 홉에서 왔는지 구분한다.

## 9. 평가 재현성

- **통화마다 고유한 `customer_id`**: `cust-<call_id>` (call_id는 통화마다 uuid). 같은 시나리오를 반복해도 앞 통화의 변경(카드 정지 등)이 새지 않는다. 목업 저장소 초기화 로직이 따로 필요 없고, 로그의 call_id로 바로 찾는다.
- **픽스처**: 러너가 통화 시작 때 `/_fixtures`로 시나리오의 고객 CRM과 `tool_failures`를 심고, 끝나면 지운다. `/_fixtures`는 평가·개발 모드에서만 켠다.
- **버전 기록**: 실행 메타데이터에 카탈로그 YAML 해시, MCP 서버·도메인 API 커밋을 남긴다. 결과가 달라졌을 때 카탈로그 변경 때문인지 바로 구분한다.
- **평가 호환**: 시나리오 형식·채점·판정기는 그대로다. 채점은 에이전트 trace를 보므로 trace 형식을 유지한다. 지연은 홉 두 개만큼 늘어나므로 기준선 비교 시 감안한다.

## 10. 등록 흐름 (실서비스 기준)

1. **팀**: 도메인 API를 구현하고 계약 테스트를 통과시킨 뒤 카탈로그 항목을 제출한다. 위험도 값은 제안만 한다.
2. **승인**: 위험도·실행 조건·이름 중복·엔드포인트 존재를 확인한다.
3. **반영**: MCP 서버 리로드 → 에이전트 리로드 (4-1). **에이전트는 재배포하지 않는다.** 진행 중인 통화에는 적용되지 않는다.
4. **평가**: 영향받는 시나리오만 실행한다. 카탈로그 변경은 배포가 아니므로 이 평가가 사실상 배포 게이트다.

데모에서는 카탈로그 파일 수정 → 리로드 → 해당 시나리오 평가로 같은 흐름을 재현한다. 승인은 `approved_by` 필드로만 표시한다. 버전은 필드만 두고 `1`로 고정한다.

## 11. 현재 코드와의 대응

| 현재 | 설계 후 |
|---|---|
| `ToolSpec` (`registry.py`) | 카탈로그 항목 → `tools/list` |
| `spec.fn(state, **args)` (`registry.py:88`) | MCP `tools/call` → 도메인 API |
| `registry.run`의 `bad_args`·`bad_value` 검사 | 에이전트 형식 검증 (`inputSchema` 기준으로 범용화) |
| `mock.py` 함수들 | 도메인 API 핸들러 |
| `ToolSpec.precheck` (`_known_card`) | 근거 검증(에이전트, `grounded_by`) + 사실 검증(도메인 API)으로 분리 |
| `guardrails/gate.py`가 `ToolSpec` 읽음 | 동일 (MCP 메타데이터 값을 읽음) |

루프·워커·프로토콜은 거의 바뀌지 않는다. 모델이 보는 도구 목록·파라미터 형식과 모델이 도구를 부르는 방식도 그대로다.

### 11-1. 옮기기만으로 안 되는 부분

1. **시나리오 데이터 주입**: 지금은 시나리오의 고객 CRM과 장애 주입이 `state.ctx.customer`로 들어가 도구 함수가 바로 읽는다(`mock.py` `_customer`·`_fail_if_injected`). → 9절의 픽스처 방식으로 대체.
2. **precheck 시점**: `loop.py:379`에서 확인 질문 **전에** `precheck`(`_known_card`)가 돈다 — 틀린 카드면 확인 질문을 하지 않는다. 검사를 도메인 API의 실행 처리로만 옮기면 실행 시점으로 밀려 동작이 바뀐다. → **에이전트 근거 검증으로 대체** (`loop.py:290`·`:379`의 `spec.precheck` 자리). 이번 통화의 조회 결과로 검사하므로 dry-run 호출이 필요 없다.
   - `_known_card`는 독스트링은 「조회된 카드 ID인가」지만 실제로는 고객 CRM의 카드 전체와 대조한다. 바뀌면 **조회 없이 올바른 `card_id`로 바로 호출하는 경우가 막힌다.** 카드 분실 프로토콜이 조회를 먼저 하므로 영향은 작을 것으로 보이나 전체 회귀에서 확인한다.
3. **테스트**: 테스트 파일 14개 중 3개가 레지스트리·목업을 직접 쓴다 → 수정 필요.
4. **도구가 에이전트 상태를 바꾸는 경우**: `request_app_auth`(`mock.py:57-63`)는 `state.authenticated`·`state.auth_failures`를 직접 바꾸고, 게이트가 이 값을 읽는다. 도메인 API는 에이전트 상태를 바꿀 수 없다. → 카탈로그에 **효과를 선언**한다: `csagent/effects: [authenticate]`. 에이전트는 이 효과가 있는 도구의 결과가 `status: success`면 인증 상태를 켜고, 아니면 실패 횟수를 올린다. 도구 이름을 에이전트에 박지 않고, 인증 상태는 API 결과에서만 나온다.
   - 실행 도구의 `executed`·`succeeded` 기록(`registry.py:93-95`)은 지금도 `risk: execute` 기준의 범용 처리라 에이전트 어댑터에 그대로 둔다.
5. **통화 컨텍스트와 업무 데이터의 분리**: 시나리오의 `context.customer`에는 둘이 섞여 있다.
   - **통화 컨텍스트 (에이전트에 남김)**: `name`(`loop.py:498`), `outbound_task`(`controller.py:95`) — 실서비스에서 CTI가 통화 시작 시 주는 정보
   - **업무 데이터 (도메인 API 픽스처로)**: `orders`·`transfers`·`cards`·`seller`, 목업 조절값 `auth_result`·`tool_failures`, 기준일 `today`(조회 결과에 들어감)
   - 시나리오 YAML 형식은 바꾸지 않는다. 러너·웹 서버가 통화 시작 시 두 부분으로 나눠 넘긴다.
6. **웹 화면의 고객 CRM 패널**: 지금은 `ctx.customer`를 그대로 보여 주고, 목업 도구가 이 딕셔너리를 직접 바꿔서(`card["status"] = "일시정지"`) 화면에 반영됐다. 분리 후에는 이 연결이 끊긴다. → 화면은 도메인 API의 `/_fixtures/<customer_id>` 조회로 현재 데이터를 읽는다 (실서비스의 상담 화면이 업무 시스템을 조회하는 것과 같다).

- **효과 선언**: `request_app_auth`가 에이전트 상태(`authenticated`·`auth_failures`)를 직접 바꾸던 것 → 카탈로그 `effects: [authenticate]`, 에이전트가 결과의 `status`로 반영. 실패 횟수는 도메인 API(인증 서비스)도 고객별로 센다
- **통화 컨텍스트 분리**: 시나리오 `context.customer` 중 `name`·`outbound_task`는 에이전트에, 나머지(업무 데이터·`auth_result`·`tool_failures`)는 도메인 API로 (`domain/store.py` `FIXTURE_KEYS`). 시나리오 YAML 형식은 그대로
- **`mock.py` 삭제**: 목업 로직은 도메인 API 한 곳에만 둔다. 테스트도 `tests/local.py`의 로컬 스택(세 층을 한 프로세스, 실제 MCP·도메인 API 경로)으로 돈다
- **오프라인 채점**: 저장된 통화 재채점(`scripts/rejudge.py`)은 카탈로그 메타데이터만 읽는 `stack.offline_registry()`
- **절차 감사(`evaluation/procedure.py`)는 `request_app_auth` 이름을 그대로 본다** — 에이전트와 독립된 감사자라 효과 선언에 의존하지 않게 둔다
- **웹 화면 CRM**: `GET /api/sessions/{id}/crm`이 도메인 API의 현재 데이터를 돌려준다. 화면(web/)은 아직 이 경로를 쓰지 않는다 (통화 시작 때 받은 고객 정보를 그대로 표시)

**실측 (실제 HTTP, 프로세스 3개)**
- 홉 지연 (에이전트 → MCP → 도메인 API 왕복, 조회 30회): 중앙값 **6.0ms**, p90 8.6ms, 최대 24.8ms(첫 호출). 그중 MCP → 도메인 API 4.3ms

## 14. 안내 항목 카탈로그 + 링크 가드레일 (2026-10-19, 러프 버전)

**문제**: `send_app_link.target`이 자유 문자열이라 모델이 같은 항목을 여러 이름으로 보냈다. 실측 결과(`runs/` 집계)는 「페널티 소명 가이드」 260회, `penalty_appeal_guide` 212회, 잘린 값(`penalty_appeal_guid` 등) 5회, 앱 경로 통째(「토스 앱 → 전체 → 토스뱅크 → …」) 4회.

**결정**
- 안내 항목 = `{id, name, audience, doc_id}` — `csagent/domain/guides.yaml`, 15개를 손으로 등록 (S1·S3·S4·S5·O1용, 셀러 1개는 셀러 인바운드용으로 미리)
- **url은 파일에 적지 않는다.** 도메인 API가 시작할 때 지식 베이스(`chunks.jsonl`)의 그 `doc_id` url로 채우고, 없으면 시작을 멈춘다 (`domain/guides.py`)
- 앱 화면(「주문 내역」)은 실제 URL이 데이터에 없다 → 그 화면 표식(`[앱 링크: 주문 내역]`)이 있는 FAQ(4705)로 보낸다. 앱 화면과 문서를 따로 두지 않고 항목 하나로 합침
- 도구 이름·인자 이름(`send_app_link`·`target`)은 그대로, 값만 enum (`catalog/notify.yaml`, version 2). 카탈로그에 `enum` 필드를 추가해 `inputSchema`로 내보내고, 에이전트는 기존 `choices` 검증으로 막는다. 도메인 API도 모르는 id는 `UNKNOWN_GUIDE` (뒷단)

- 말 쪽: 발화에 URL·도메인 모양이 나오면 **등록 여부와 상관없이** 그 지점부터 문장 끝까지 지운다 (`guardrails/links.py`, 기록 `link_blocked`). 전화로 URL을 읽어 주는 것 자체가 맞지 않음. 스트리밍은 기존 번호 검사(`SpeechScreen`)가 숫자뿐 아니라 영문에서도 문장 끝까지 붙잡도록 넓혔고, 「영문·숫자.」 뒤 마침표는 다음 글자가 공백일 때만 문장 끝으로 본다 (toss.im · 1.5)
- 두 목록(카탈로그 enum ↔ `guides.yaml`)이 같은지는 `tests/test_guides.py`가 확인
