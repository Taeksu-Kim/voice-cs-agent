# 10. 관측과 재현 — 자동 개선 루프의 바탕

목표 흐름: **이상 탐지 → 이력 확인 → 분석 → 수정 → 재현**을 Claude Code가 돌린다 (외부 API 없이, 스킬 + `claude -p`).
판정·반영은 사람이 승인한다. 이 문서는 그 바탕인 로깅·좌표·재현 설계다.

## 1. 로깅 점검 (10/21)

| 단계 | 있던 것 | 빠졌던 것 → 조치 |
|---|---|---|
| 이력 | trace(턴별 라우팅·검색·LLM·도구·게이트·가드레일·들린 말), `llm_calls.jsonl`(호출별 입력·출력 원문, trace와 `call_id`로 연결), 평가 채점 항목, 서버 `calls.jsonl` | **버전**: dirty 실행의 변경 내용·서빙 모델이 없었고, 서버 통화엔 커밋도 없었음 → 2절 |
| 재현 | 대화 이력, 그 턴의 LLM 입력 원문 | **턴 시작 상태**(업무·단계·걸린 질문·조회 기록·슬롯·결과 모르는 실행)와 **도메인 초기 데이터** → 3절 |
| 위치 지정 | 턴 번호 | **스텝·절차 위치** → 3절 좌표 |
| 탐지 | 가드레일 이벤트(trace), 평가 채점 | 실시간 통화 사후 판정 없음 → 4절 (미구현) |
| 음성 | STT 텍스트, 재생 보고 | 원음 미저장 — STT 오류는 분석 불가 (지시문 개선 범위 밖, 보류) |

## 2. 버전 기록

- `stack.git_version()`: 커밋 + dirty + `diff_sha`(변경 내용 해시)
- `stack.record_versions()`: 위 + 카탈로그 해시 + 모델(설정값과 LLM 서버가 실제 서빙 중인 id). dirty면 `code_<diff_sha>.diff`를 같은 폴더에 남김
- 평가: `runs/<실행>/run_meta.json` · 서버: `logs/<날짜>/server_meta.jsonl`(기동마다 한 줄), 끝난 통화 기록마다 `version`
- 판정기·시뮬레이터 버전은 코드(커밋 + diff)에 들어 있다. 샘플링 온도는 기본 0이지만 vLLM 배치·검색이 완전 결정적이지 않다 → 재현은 「N번 중 몇 번」으로 본다

## 3. 좌표

이벤트마다 두 축을 찍는다 (`csagent/agent/trace.py`):

| 필드 | 형식 | 뜻 |
|---|---|---|
| `at` (시간 축) | `t2.s1.gate` | 2턴 · 1번째 LLM 스텝 · 게이트 (같은 스텝에 같은 종류가 또 나오면 `#2`) |
| `where` (절차 축) | `card_loss/confirm` | 업무 / 프로토콜 단계 |

- 스텝 0 = LLM 전(라우팅·검색), 1부터 LLM 스텝. 한 턴에 워커가 바뀌어도 이어 센다
- 통화 전체 주소: `<call_id>@t2.s1`
- `t<턴>.s0.state`: 턴 시작 상태 스냅샷 (`CallState.snapshot()`), `t0.s0.call_open`: 도메인 초기 데이터
- 좌표 없는 예전 trace는 `tracegraph.coords`가 llm 이벤트 순서로 스텝을 추정

### 그림

`python scripts/trace_graph.py runs/<실행> <시나리오>[:반복]` 또는 `logs/<날짜> <call_id>` → mermaid 흐름도.
노드 id = 좌표(`t2_s1_gate`), 턴 = subgraph(절차 경로·고객 발화), 빨강 = 오류·실패, 주황 = 가드레일 발동, 맨 위 = 채점 실패 항목.

예: `20261021_010852_C s3_b0_defect` — 그림에서 바로 보이는 것: 150자 초과는 t1의 s1(확인)·s2(사진 안내)·s3(링크·2영업일)이 한 턴에 이어 들린 것, 반복은 t2·t3 s1의 같은 말.

## 4. 이상 탐지 (10/24 구현 — `csagent/anomaly.py`, `scripts/detect.py`)

탐지는 분석할 **후보를 고르는** 일이라 정밀할 필요가 없다 (거르는 건 분석하는 쪽). 다만 신호마다 이상하다고 볼 이유가 분명해야 한다. 세 층:

| 층 | 방식 | 상태 |
|---|---|---|
| 확실한 신호 | trace·이력 규칙 | 구현. **bad**: 턴 오류 · 결과 모름 · 대체 문장(못 들었어요·문제가 생겼어요). **warn**: 도구 실패(백엔드 탓일 수 있음) · 반복 · 150자 초과 · 턴 한도 종료 · 미해결 종료(서버 통화만 — 평가는 disposition 채점이 기대값과 비교) |
| 판정기 신호 | 평가 기록은 채점 실패 항목 그대로, 서버 통화는 `--judge`로 근거 판정 v4 | 구현 (서버 통화 판정은 근거 항목만) |
| 비율 변화 | 기간별 통계 | 미구현 — 실제 트래픽 생긴 뒤. 집계 바탕은 `csagent/monitoring.py`(지표) |

- **가드레일 발동은 신호가 아니라 맥락**: 결함은 이미 막혔다. 통화별·전체 발동 수만 센다 (잦으면 지시문 개선 후보 — APO 입력)
- 신호에 좌표(`t3`, `t3.s1`)를 붙인다 — 채점 항목도 근거 판정은 「3턴: …」에서 턴을 뽑는다
- 규칙 신호와 겹치는 채점 항목(no_repeat·voice_length)은 규칙 쪽(위치가 있다)만 남긴다

```
python scripts/detect.py runs/<실행> [logs/<날짜> --judge] [--level bad]
→ runs/cases/<시각>/summary.md · <출처>_<키>/{case.json, trace.md, llm_calls.jsonl, repro.yaml}
```

**케이스 묶음**: case.json(출처·신호·가드레일 발동·버전) · trace.md(mermaid, 맨 위에 신호) · llm_calls.jsonl(그 통화의 LLM 원문만) ·
repro.yaml(재현 명세 **초안** — 가장 심한 신호를 술어로 옮김: 150자 초과 → `len_over`, 반복 → `repeat`, 채점 실패 → continue + `check`.
턴 시작 상태가 없는 10/21 전 기록은 step 모드 · 그 턴 첫 스텝. 도구 실패처럼 술어로 못 옮기는 신호는 `fail_if`가 비어 재현기가 거절 — 분석 후 정한다)

### 확인 (10/24)

- `20261020_071342_C`(기준선 50통화): 케이스 7. **채점 실패 5건 전부 잡힘**(150자 초과 2 · 반복 1 · 근거 1 · 결과 불일치 1) + s5_h8 2건(백엔드 시간 초과 → 결과 모름, 시나리오가 의도한 상황 — 실서비스에선 진짜 사건)
- 가드레일 발동 전체: 보류한 말 버림 26 · 들리지 않은 결과 게이트 11 · 동의 필요 게이트 10
- 탐지 → 묶음 → 재현 한 바퀴: `010852 s3_b0_defect r0` 묶음의 repro.yaml 그대로 `scripts/repro.py` → 실패 2/2 (같은 175자)

## 5. 재현 (10/21 구현 — `csagent/evaluation/repro.py`, `scripts/repro.py`)

구간 선택은 Claude, 실행은 고정된 재현기. Claude가 내는 것은 **재현 명세**뿐이다:

```yaml
case: runs/20261021_010852_C/s3_b0_defect/r0
from: t1.s2          # 좌표 — 이 지점 직전 상태에서 시작
mode: turn           # step: 같은 입력 그대로 (모델 흔들림 확인) / turn: 지금 코드·지시문으로 그 턴 / continue: 시뮬레이터로 이어서
repeat: 10
fail_if: utterance_len > 150   # 판정 항목 이름·정규식도 가능 — 수정 전에 정하고 수정 후에도 그대로
```

- 결과는 「수정 전 7/10 → 수정 후 1/10」. 기준(`fail_if`)을 수정 뒤에 바꾸지 않는다
- 끝에 관련 시나리오 회귀를 붙여 한 케이스 과적합을 막는다
- 상태 복원: `t<k>.s0.state` + 그 전까지 이력·trace + 시나리오 픽스처 + 그 전 턴의 성공한 실행(execute·notify)을 도메인에 다시 적용
- continue의 고객: `customer: recorded`(기본, 기록된 고객 말 순서대로 — 에이전트 변화만 본다) | `simulator`
- 술어: `len_over` · `repeat` · `regex` · `tool` · `no_tool` · `event` · `gate` · `disposition` · `check`(채점 항목, continue만). step 모드는 출력 하나만 보므로 `len_over`·`regex`·`tool`·`no_tool`만
- 결과: `runs/repro/<시각>_<키>_<좌표>_<모드>/` — spec.json · repro.jsonl · run_meta.json(버전) · llm_calls.jsonl
- 10/21 상태 복원 이전 기록(state 스냅샷 없음)은 step 모드만

### 확인 (`runs/20261021_010852_C` s3_b0_defect r0)

| 명세 | 결과 | 읽기 |
|---|---|---|
| `at: t1, turn, len_over: 150` | 5/5 실패 (매번 같은 175자) | 온도 0이라 턴 재현이 거의 결정적 — 수정 전후 비교에 쓸 수 있다 |
| `at: t1.s2, step, len_over: 80` | 3/3 (같은 85자) | 그 스텝 하나는 85자 — 150 초과는 한 턴에 세 스텝의 말이 이어져서 (구조 문제) |
| `at: t2, continue, simulator, check: no_repeat` | 0/2 | 시뮬레이터가 이번엔 바로 수긍 → 반복이 안 생김 |
| `at: t2, continue, recorded, check: no_repeat` | 2/2 | 같은 반박을 다시 들으면 같은 답 — 고객 말을 고정해야 에이전트 결함이 재현된다 |

## 6. 개선 루프 — triage · APO (10/25)

탐지가 만든 케이스를 Claude Code 스킬이 분석하고, 지시문이 원인이면 수정 후보를 만들어 테스트한다. **어느 단계도 저장소를 고치지 않는다** — 반영은 사람이 결정한다.

```
detect.py → 케이스 묶음 → /triage → layer: prompt → /apo → /apo-test plan → apo_test.py run-all → /apo-test review → case_report.py
                                  └ guide · doc · code → 사람에게 제안 / judge → 판정기 검증 세트 / env → 조치 없음
사람 승인 → 저장소에 반영 → apo_test.py verify → 리포트 4절(반영 후 확인)
```

| 단계 | 하는 일 | 산출물 | 막아 둔 것 |
|---|---|---|---|
| `/triage` (`.claude/skills/triage/`) | 판정기 오판 확인 → 재현 기준치 → 원인 층 6개(prompt·guide·doc·code·judge·env) → 제안 | `triage.md`, `runs/triage/index.jsonl` (`scripts/triage_save.py`가 형식 검사) | 수정 도구 권한 없음, 결과 본 뒤 기준 변경 금지, 실패를 통과시키려는 가이드 지어내기 금지 |
| `/apo` (`.claude/skills/apo/`) | 근본 요구사항 → 후보 2~3개 → 원칙 점검 → 기존 지시문과 모순 검토 | `runs/apo/<실험>/<후보>/` 사본·diff·근거 (`scripts/apo_candidate.py`) | 단계·조건·도구 변경 거부(코드 층), 저장소 지시문 불변 |
| `/apo-test` plan·review | 테스트 계획(target 고정·변형·부작용 변형·guard·회귀·케이스 모음) / 출력 근거 대조·선택 | `tests.yaml`, `proposal.md` | 재현·평가를 직접 돌리지 않음(실행기 몫) |
| `apo_test.py run-all` | 후보마다 `CSAGENT_PROTOCOL_OVERRIDE`로 끼워 실행. 단계별 거르기(target에서 못 고친 후보는 이후 생략), 이어 돌리기, 잠금 | `results.jsonl` | Claude 밖에서 실행 — 제한 시간·권한 문제 없음 |
| `case_report.py` | 탐지 → triage → APO → 반영 후 확인을 한 장으로 | 케이스 폴더 `report.md` | 판단 없이 모으기만 |
| `suite.py` | 업무별 케이스 모음(defect·guard) — apo-test 계획에 `suite: <업무>` | `runs/suite/<업무>.yaml` | — |

**프롬프트 작성 원칙** (`.claude/skills/apo/reference/principles.md`): ① 모델이 아는 것은 쓰지 않는다 ② 생각 순서 대신 고려할 항목 ③ 땜질 규칙 대신 근본 요구사항
④ 금지 대신 원하는 방향 ⑤ 기존 지시문과 모순 검토 — 1~5는 사용자가 정함. 첫 실험 뒤 더한 것: ⑥ 행동을 넓히는 지시엔 근거 범위를 함께 ⑦ 후보가 새로 부를 실패를 미리 적기 ⑧ 지운 문장이 막던 과거 실패 확인

### 6-1. 실험 ① 실제 결함 — `s3_b0_defect` 반복 (정답 없음)

triage: 반복 금지 지시가 「고객이 같은 말을 다시 하면」에만 걸려, 고객이 새 질문을 붙이면 조건에 안 걸린다 → prompt 층 (재현 5/5). 같은 통화의 150자 초과는 code 층으로 분리.

| 라운드 | target | 결론 | 떨어진 이유 |
|---|---|---|---|
| 1 (원칙 1~5) | A·C 5/5 → 0/5 | **추천 없음** | 「새 질문에 문서로 답하라」로 넓히자 문서에 없는 화면·버튼을 지어냄, 10/19에 고친 「사진 없이도」 재발 |
| 2 (원칙 1~8) | A·B 5/5 → 0/5 | **추천 없음** | target이 turn 모드라 앞 턴을 기존 지시문이 만든 말로 고정 — 그 전 턴부터 이어 돌린 guard(continue)에서는 모든 후보가 3/3 반복. 출력에도 문서 밖 표현이 남음 |

- 읽기: 이 결함은 지시문만으로 안 고쳐질 가능성이 있다 (FAQ에 화면 단위 절차가 없어, 「답하라」고 하면 모델이 채운다 — doc 층 후보). 검증 단계가 「0/5」 착시와 지어내기를 걸러 낸 것이 이 실험의 결과
- 규칙으로 남긴 것: 앞 턴 대화에 의존하는 결함(반복 등)은 재현 기준을 continue 모드로 (triage·apo-test)

### 6-2. 실험 ② 일부러 낸 구멍 — 정답이 있는 결함

**답 가리기**: 저장소 밖 별도 폴더에 현재 파일을 복사하고 `git init`을 새로 (원래 문장이 이력·diff·reflog 어디에도 없게), 원래 저장소 경로 읽기 금지 설정, 판정 기록(`labels/`) 제외, 정답 파일은 실험 폴더 밖에 보관.
dirty 실행이 남기는 변경 내용 파일(`code_*.diff`)에도 지운 문장이 들어가므로 구멍을 낸 상태로 커밋하고 실행 기록을 지운 뒤 다시 돌렸다.

**구멍 찾기**: 지운 문장 3개 중 2개는 지워도 행동이 안 바뀌었다 (3/3 통과)
- `card_loss` 「인증이 안 된다고 해도 먼저 한 번 보낸다」 — auth 단계의 다른 지시가 같은 행동을 끌어냄 (방어가 두 겹)
- `general` 「일반 질문이면 조회하지 말고 바로 답한다」 — 모델이 원래 그렇게 행동함 (원칙 1에 비추면 불필요한 문장)
- `exchange_return` guide 단계 「단순 변심이면 `send_app_link(target=exchange_refund_request)`로 안내를 보낸다」 → milestones 2/3 실패 (링크를 `order_history`로) — **이것으로 실험**

| 단계 | 결과 |
|---|---|
| 탐지 | 3통화 중 2통화 `check:milestones` bad |
| triage | 원인 「그 분기에만 링크 지정이 없다」, 수정 방향이 지운 문장과 같음 (재현 3/5). 같이 걸린 근거 판정 실패는 판정기 오추출(고객 말 되받기)로 분리 |

### 6-3. 운영에서 배운 것

- **오래 걸리는 실행은 LLM 세션 밖으로**: `claude -p` 안에서 재현이 Bash 제한 시간(기본 2분, 스킬에 적은 10분)을 넘으면 백그라운드로 넘어가고 세션이 끝난다. 이어진 세션은 스킬 권한이 풀려 저장도 못 한다 → 스킬은 판단만, 재현·평가는 실행기(`run-all`)가. 실행 환경엔 `BASH_DEFAULT_TIMEOUT_MS`·`BASH_MAX_TIMEOUT_MS`
- **로컬 벡터 DB(Milvus Lite)는 한 프로세스만 연다** → 실행기 잠금으로 줄 세우기 (병렬은 서버 방식 DB가 필요)
- **비용**: 재현기가 continue 모드면 술어와 무관하게 LLM 판정기를 돌리고 있었다 → 술어에 LLM 판정 항목이 있을 때만 (칸당 6~7분 → 1분 20초). 회귀는 기본 규칙 채점만(말 내용은 review가 출력을 직접 본다), 바뀐 분기를 지나는 시나리오만, 반복 target 3·변형 2
