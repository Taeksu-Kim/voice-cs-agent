# 05. 에이전트 구조는 어떻게 고르나 — 우리 상황에서 C'를 택한 이유

> 에이전트 설계가 익숙하지 않은 상태에서 읽어도 따라올 수 있게, 기본 개념 → 고려사항 → 우리 상황 → 결론 순서로 설명한다.
> 결론 요약: **결정적 워크플로를 중심에 두고, LLM은 고객 말을 이해하고 응답을 만드는 데 쓰는 하이브리드 구조 (C')**
> 관련 문서: [04_에이전트_구조_검토.md](04_에이전트_구조_검토.md) (후보 비교·외부 검토 원문)
> 작성: 2026-10-12

---

## 1. 에이전트 구조에서 정해야 하는 단 하나의 질문

에이전트 구조를 고를 때 이름(ReAct, 멀티에이전트, 오케스트레이터…)부터 보면 헷갈린다. 본질적인 질문은 하나다.

> **무엇을 LLM이 결정하게 하고, 무엇을 코드가 결정하게 할 것인가?**

상담 에이전트가 한 턴에 하는 일을 쪼개면 이렇다.

| 하는 일 | 예 | 누가 정할 수 있나 |
|---|---|---|
| 고객 말 이해 | 「카드 잃어버렸는데 정지 말고 아예 신고해 주세요」에서 의도와 정보 뽑기 | **LLM이 필요** — 말은 자유롭다 |
| 다음에 무엇을 할지 | 본인 확인부터? 카드 선택부터? 실행? | LLM도 코드도 가능 |
| 도구 실행 허락 | 지금 분실신고를 실행해도 되나 | LLM도 코드도 가능 |
| 응답 만들기 | 「확인했어요, 분실신고로 진행할게요」 | **LLM이 유리** — 자연스러운 말 |

가운데 두 줄을 **누구에게 맡기느냐**가 구조를 결정한다. 이것을 **LLM의 자율성 수준**이라고 부른다.

---

## 2. 자율성 스펙트럼 — 구조의 종류

왼쪽일수록 코드가, 오른쪽일수록 LLM이 결정한다.

```
코드가 결정 ◀───────────────────────────────────────────────────▶ LLM이 결정
 규칙 챗봇   │  워크플로 + LLM  │  라우팅·핸드오프  │  ReAct 단일  │  오케스트레이터-워커  │  완전 자율
```

| 구조 | 어떻게 동작하나 | 강점 | 약점 |
|---|---|---|---|
| **규칙 챗봇** | 정해진 시나리오 버튼·키워드로 진행 | 예측 가능, 빠름 | 자연어를 못 알아들음. 토스뱅크가 이것을 LLM 에이전트로 바꿨다 |
| **워크플로 + LLM** | 진행 순서는 코드(상태 머신), 각 단계에서 LLM이 말 이해·응답 | 순서·규정 보장, 테스트 쉬움 | 예상 못 한 흐름에 경직될 수 있음 |
| **라우팅·핸드오프** | 처음에 업무를 판별해 업무 전용 처리기로 넘김 | 업무별로 분리돼 관리 쉬움 | 판별이 틀리면 엉뚱한 처리기로 감 |
| **ReAct 단일** | LLM 하나가 모든 도구를 들고 매 스텝 「도구 쓸지·답할지」를 스스로 결정 (생각→행동→관찰 반복) | 유연, 구현 간단 | 순서·규정을 프롬프트에만 의존, 업무가 늘수록 프롬프트가 비대해짐 |
| **오케스트레이터-워커** | 관리자 LLM이 일을 나눠 전문 LLM들에게 맡기고 결과를 합침 | 복잡한 일을 분해·조합 | LLM 호출이 많아 느리고 비쌈 |
| **완전 자율** | 목표만 주면 스스로 계획·실행·수정 | 열린 문제 | 통제·예측 어려움 |

**어느 것이 「더 좋은」 구조는 없다.** 문제의 성격에 맞는 자율성 수준이 있을 뿐이다.

## 3. 구조를 고를 때 보는 고려사항

| # | 고려사항 | 질문 | 자율성을 낮추는 쪽 (코드) | 자율성을 높이는 쪽 (LLM) |
|---|---|---|---|---|
| ① | **업무가 정형적인가** | 절차가 정해져 있나 | 정해져 있음 | 매번 다름 |
| ② | **실행이 위험한가** | 잘못 실행하면 되돌릴 수 있나 | 되돌리기 어려움 (돈, 카드 정지) | 조회·안내뿐 |
| ③ | **지연 예산** | 응답이 얼마나 빨라야 하나 | 엄격 (전화) | 느슨 (배치, 리포트) |
| ④ | **자원** | LLM 호출 1번이 얼마나 비싼가 | 비쌈 (GPU 1장) | 저렴 |
| ⑤ | **입력이 비정형인가** | 사용자 말이 자유로운가 | — | 자유로움 → **이해 단계에는 LLM 필요** |
| ⑥ | **업무가 늘어나는가** | 앞으로 업무가 추가되나 | — | — (이건 **분리**를 요구: 업무별로 나눠야 관리됨) |
| ⑦ | **평가·디버깅** | 실패 원인을 찾고 고칠 수 있나 | 분리돼 있을수록 쉬움 | 한 덩어리일수록 어려움 |
| ⑧ | **여러 업무가 섞이나** | 한 요청에 일이 여러 개인가 | 드묾 | 잦음 → 분해·조합 필요 |

## 4. 우리 상황을 대입하면

| # | 우리 상황 | 방향 |
|---|---|---|
| ① 정형성 | 카드 분실·착오송금·반품·아웃바운드 고지 — **대부분 절차가 정해져 있음** | → 코드 |
| ② 위험 | 카드 정지·분실신고는 실제 실행. 금융권이라 **인증 전 실행·재확인 누락은 사고** | → 코드 |
| ③ 지연 | **전화**. 현재 27B 모델로 첫 글자까지 약 2.8초 — 호출이 하나 늘면 바로 체감됨 | → LLM 호출 최소화 |
| ④ 자원 | **GPU 1장, 로컬 27B 하나** | → LLM 호출 최소화 |
| ⑤ 입력 | 고객 발화는 자유롭고, STT 오류까지 섞임 | → **이해·응답은 LLM** |
| ⑥ 확장 | 커머스·광고 → CX → 계열사 → 외부 고객사로 **업무가 계속 늘어남** | → 업무별 **분리** |
| ⑦ 평가 | 시나리오 기반 자동 평가로 **개선 효과를 수치로** 보여야 함 | → 분리 + 결정적 검사 |
| ⑧ 다중 업무 | 대부분 업무 1개. 「카드 분실 + 모르는 결제」 같은 경우는 **드물지만 중요** | → 분해 엔진까지는 불필요, 순서 관리만 |

정리하면 우리 문제는 이렇게 생겼다.

> **입력(고객 말)은 비정형인데, 업무 실행은 정형적이고 위험하며, 지연과 자원은 빠듯하고, 업무는 계속 늘어난다.**

---

## 5. 그래서 구조를 한 단계씩 정하면

### 단계 1. 실행 순서와 실행 허락은 코드가 정한다 ← ①②
카드 분실은 「본인 확인 → 처리 선택 → 재확인 → 실행」이 바뀌면 안 된다. 이것을 프롬프트로 「반드시 지켜라」라고 쓰는 것과, 코드가 **조건을 만족하지 않으면 실행 도구 자체를 못 쓰게** 하는 것은 안전성이 다르다. LLM은 확률적이라 수천 번 중 몇 번은 규칙을 건너뛴다.

→ **ReAct 단일·오케스트레이터처럼 실행 순서까지 LLM에 맡기는 구조는 여기서 불리해진다.**

### 단계 2. 고객 말 이해와 응답은 LLM이 한다 ← ⑤
「정지 말고 아예 신고로요, 본인 맞고요」 같은 말을 규칙으로 처리하면 옛날 챗봇이 된다. 이 부분은 LLM이 해야 한다.

→ **규칙 챗봇은 탈락.** 코드가 순서를 쥐고, 각 단계 안에서 LLM이 말을 이해·생성하는 **워크플로 + LLM**이 출발점이 된다.

### 단계 3. 턴마다 LLM 호출 수를 늘리지 않는다 ← ③④
관리자 LLM이 매 턴 「누구에게 맡길지」 판단하고 결과를 다시 합치면 턴당 호출이 2~3번이 된다. 전화에서 첫 응답이 1~2초 더 늦어진다.

→ **동적 오케스트레이터-워커는 탈락.** 업무 판별이 필요한 순간에만 판별하고, 진행 중인 업무는 바로 처리한다.

### 단계 4. 업무별로 나눈다 — 단, 필요한 곳에서만 ← ⑥⑦
업무마다 **프롬프트·허용 도구·절차**를 따로 두면, 새 업무를 추가해도 다른 업무가 망가지지 않고(회귀 방지), 실패를 업무별로 측정·개선할 수 있다. 이 업무 단위 처리기를 **워커**라고 부른다.
다만 업무 개수만큼 쪼갤 필요는 없다. 배송 조회와 주문 상태 확인처럼 절차·권한이 같으면 한 워커로 충분하다. **절차·도구 권한·상태 관리가 실제로 다른 곳에서만 나눈다.**

> 워커 = 반드시 별도 모델이 아니다. **같은 27B 모델 하나**를 쓰면서 업무별로 프롬프트·도구·상태만 다르게 적용한다. GPU에 모델을 여러 개 올릴 필요가 없다.

### 단계 5. 업무 전환과 순서 관리는 코드(세션 컨트롤러)가 한다 ← ⑧
「카드 잃어버렸는데 모르는 결제도 찍혔어요」 → 업무가 2개. 이걸 위해 관리자 LLM을 둘 필요는 없다. 코드가 **업무 대기열**을 들고 「카드 보호 조치 먼저, 부정 사용 건은 대기」처럼 순서를 관리하면 된다.

그런데 고객이 업무 도중 다른 이야기를 꺼내는 건(주제 전환) 누가 알아채나? 매 턴 별도 LLM으로 분류하면 단계 3이 깨진다. 그래서 **3겹으로 나눈다.**

| 겹 | 누가 | 무엇을 | 추가 LLM 호출 |
|---|---|---|---|
| 1 | **코드** | 확실한 신호 — 상담원 요청, 통화 종료, 사기·긴급 키워드 | 없음 |
| 2 | **현재 워커** | 고객 말을 해석할 때 「계속(continue) / 다른 업무(switch) / 애매(uncertain)」를 같이 출력 | **없음** (어차피 하는 해석에 한 필드 추가) |
| 3 | **라우터** | switch·uncertain이거나 고위험 신호일 때만 업무 판별 | 그때만 1번 |

> 주의: 워커는 응답을 **스트리밍**한다. 출력 순서가 `say`(할 말)부터면, 나중에 switch로 판정돼도 엉뚱한 말이 이미 고객에게 나간 뒤다. 그래서 출력 순서를 **intent → 슬롯 → say**로 둔다.

### 단계 6. 정보 수집은 유연하게, 실행 조건은 엄격하게 ← ①②⑤
고객은 묻기 전에 정보를 먼저 말하기도 한다. 그래서 두 가지를 같이 쓴다.

| 장치 | 답하는 질문 | 성격 |
|---|---|---|
| **슬롯** | 어떤 정보를 이미 알고 있나 | 순서 무관 — 고객이 먼저 말하면 먼저 채움 |
| **상태 머신** | 지금 어떤 행동이 허용되나 | 엄격 — 조건이 안 되면 실행 불가 |

예: 카드 분실 중 「일시정지 말고 분실신고로 해주세요. 본인 맞고요.」

| 항목 | 상태 | 이유 |
|---|---|---|
| 처리 선택 | 분실신고 — **확보** | 고객이 말함 |
| 본인 확인 | **미완료** | 「본인 맞고요」는 인증이 아니다. 앱 인증이 성공해야 완료 |
| 대상 카드 | **미확인** | 카드가 여러 장일 수 있다 |
| 실행 재확인 | **미완료** | 실행 직전에 말로 다시 확인 |
| 분실신고 실행 | **불가** | 위 조건이 다 갖춰질 때까지 |

그리고 재확인 뒤 고객이 대상 카드를 바꾸면 **재확인은 무효**가 되어야 한다. 이런 규칙은 프롬프트가 아니라 코드에서 관리해야 안전하다.

이 실행 조건 검사를 모든 실행 도구 앞에 두는 것이 **공통 실행 게이트**다 (가드레일의 「행동」 층).

## 6. 그렇게 나온 구조: C'

```
고객 발화 (STT 결과)
   │
   ▼
┌─────────────────────── 세션 컨트롤러 (코드) ───────────────────────┐
│  · 통화 상태: 진행 중 업무, 대기 업무, 슬롯, 인증 상태               │
│  · 1겹 감지: 상담원 요청 / 종료 / 사기·긴급 신호 → 즉시 처리         │
│  · 진행 중 업무가 있으면 → 해당 워커로                              │
│  · 없으면 → 라우터(규칙 + 필요할 때만 LLM)로 업무 판별              │
└──────────────────────────────────────────────────────────────────┘
   │
   ▼
┌──── 워커 (같은 27B, 업무별 프롬프트·허용 도구·상태 머신) ────┐
│  LLM 출력: intent(continue/switch/uncertain) → 슬롯 → say     │
│  · switch/uncertain → 세션 컨트롤러가 라우터 호출            │
│  · 필요하면 지식 검색(RAG)·조회 도구                         │
└──────────────────────────────────────────────────────────────┘
   │ 실행 도구를 쓰려 하면
   ▼
┌──── 공통 실행 게이트 (코드) ────┐
│  인증됐나 / 재확인됐나 / 이 업무에 허용된 도구인가 / 중복 실행인가 │
│  → 통과해야만 실행              │
└─────────────────────────────────┘
   │
   ▼
응답 스트리밍 (→ 나중에 TTS)
```

**구성요소 요약**

| 구성요소 | 역할 | 구현 |
|---|---|---|
| 세션 컨트롤러 | 통화 상태 보관, 업무 배정·전환·대기열, 확실한 신호 처리 | 코드 |
| 라우터 | 새 업무 판별 | 규칙 우선, 애매할 때만 LLM |
| 워커 | 업무별 대화 진행 — 말 이해·슬롯 채우기·응답 | 상태 머신(코드) + LLM |
| 공통 실행 게이트 | 실행 도구 앞 정책 검사 | 코드 |
| 지식 검색 | FAQ·문서 근거 | 기존 하이브리드 검색 |
| 이관 요약 | 상담원에게 넘길 때 요약 | 구조화된 상태 + 필요 시 LLM |

**아웃바운드는 더 단순하다**: 처음부터 업무가 정해져 있으니(O1 페널티 안내, O2 광고 컨택) 라우터 없이 해당 워커로 시작한다. **고지 문구는 승인된 문구**를 쓰고, 반발 대응·질문 답변에만 생성형 응답을 쓴다.

### 한 통화 따라가기 (카드 분실)

| 턴 | 고객 | 시스템 안에서 일어나는 일 | 에이전트 |
|---|---|---|---|
| 1 | 카드를 잃어버렸어요 | 진행 업무 없음 → 라우터: 「카드 분실」 → 카드 분실 워커 배정. 워커: intent=continue, 슬롯 없음 | 많이 놀라셨죠. 먼저 본인 확인을 위해 앱으로 인증 요청을 보내 드릴게요 |
| 2 | 네 근데 정지 말고 아예 분실신고로요 | 워커: continue, 슬롯 처리선택=분실신고. 상태: 인증 미완료 → 실행 불가 | 네, 분실신고로 진행할게요. 앱에서 인증 먼저 부탁드려요 |
| (앱 인증 성공) | | 세션: 인증=완료 | |
| 3 | 했어요 | 카드 2장 → 대상 카드 확인 필요 | 토스유스카드와 체크카드 중 어떤 카드인가요? |
| 4 | 유스카드요 | 슬롯 대상=유스카드. 재확인 단계로 | 토스유스카드를 분실신고하면 실물 카드 CVC로만 해제할 수 있어요. 진행할까요? |
| 5 | 네 해주세요 | 재확인=완료 → 게이트 통과 → 분실신고 실행 | 분실신고 완료됐어요 |
| 6 | 아 그리고 모르는 결제도 있었어요 | 워커: **switch** → 컨트롤러가 「부정 사용」 업무로 전환 (규칙상 이관 대상) | 그 건은 확인이 필요해서 담당 상담원에게 연결해 드릴게요. 지금까지 내용은 전달해 둘게요 |

## 7. 다른 구조는 왜 아닌가

| 구조 | 탈락 이유 | 그래도 쓰는 곳 |
|---|---|---|
| 규칙 챗봇 | 자연어를 못 알아들음 (단계 2) | 확실한 신호 감지(1겹)에만 규칙 |
| ReAct 단일 | 순서·실행을 LLM에 맡김 (단계 1), 업무가 늘면 비대 (단계 4) | 워커 안에서 열린 질문에 답할 때 짧게 |
| 동적 오케스트레이터-워커 | 턴당 호출이 많아 느림 (단계 3) | 다중 업무가 매우 잦아지면 재검토 |
| Plan-and-Execute | 매 요청 계획 단계 → 지연 | 사용 안 함 |

### 그래도 ReAct를 기준선으로 남겨 비교하는 이유
「C'가 낫다」는 건 지금은 **설계 판단**이지 실험으로 증명된 게 아니다. 특히 단일 ReAct에 **같은 실행 게이트**만 붙여도(A1) 절차 위반은 상당히 막힐 수 있다. 그러면 C'의 장점은 「안전」이 아니라 「관리·확장·평가가 쉬움」으로 옮겨 간다.
그래서 3가지를 같은 시나리오로 비교한다.

| 실험군 | 구성 | 보려는 것 |
|---|---|---|
| A0 | 지금의 단일 에이전트 | 출발점 |
| A1 | A0 + 공통 실행 게이트 + 세션 상태 | 최소 수정으로 충분한가 |
| C' | 세션 컨트롤러 + 워커 + **같은 게이트** | 워커 분리가 추가 가치를 주는가 |

**핵심 비교는 A1 대 C'** — 게이트가 같아야 구조의 효과만 분리된다.
측정: 업무 완료율(과한 이관·거절도 실패로), 절차 위반(**로그 기반 결정적 검사**), 주제 전환 감지율·오탐률, 고위험 실행 정확도, 턴별 LLM 호출 수·첫 글자 지연(p50/p90/p99), 새 업무 추가 시 수정 범위.

## 8. 이 판단이 틀릴 수 있는 경우

| 이런 결과가 나오면 | 바꿀 방향 |
|---|---|
| A1이 C'와 비슷하게 안전하고 관리 비용도 크지 않음 | **A1 채택** (더 단순한 쪽) |
| 워커의 intent 판정이 주제 전환을 자주 놓침 | 전환 감지를 별도 분류기로 (호출 비용 감수) |
| 다중 업무 통화가 생각보다 흔함 | 오케스트레이터 쪽으로 이동 검토 |
| 상태 머신이 너무 경직돼 대화가 어색함 | 슬롯 비중을 늘리고 단계를 줄임 |

## 9. 용어

| 용어 | 뜻 |
|---|---|
| **에이전트** | LLM이 도구를 써서 목표를 수행하는 시스템. 「에이전트 = 모델 + 에이전트 하네스(루프·도구·컨텍스트·가드레일)」 |
| **ReAct** | Reason + Act. LLM이 생각 → 도구 실행 → 결과 관찰을 반복하며 스스로 진행 |
| **오케스트레이터 / 워커** | 일을 나누고 맡기는 관리자 / 맡은 일을 처리하는 실행자 |
| **라우터** | 요청이 어느 업무인지 판별해 담당에게 보내는 장치. 오케스트레이터보다 가볍다 (계획·종합을 안 함) |
| **핸드오프** | 한 처리기가 대화를 다른 처리기에 넘기는 것 |
| **워크플로 / 상태 머신** | 단계와 단계 사이 이동 조건을 코드로 정의한 흐름 |
| **슬롯** | 업무 처리에 필요한 정보 칸 (처리 선택, 대상 카드, 사유 …) |
| **세션 컨트롤러** | 한 통화의 상태와 업무 배정을 관리하는 코드 |
| **실행 게이트** | 실행 도구 앞에서 조건(인증·재확인·권한·중복)을 검사하는 코드 |
| **가드레일** | 에이전트가 위험하거나 틀린 행동을 못 하게 막는 장치들 (입력·행동·출력·대화 층) |
| **HITL** | Human-in-the-loop. 실행 전 사람의 확인을 받는 것. 상담에서는 「고객의 말로 하는 재확인」 |
| **결정적 검사** | 같은 입력에 항상 같은 결과를 내는 검사 (코드 규칙). LLM 채점과 대비 |
