# 04. 에이전트 구조 검토 — ReAct 단일 vs 오케스트레이터-워커

> 외부 검토용 독립 문서. 이 문서만 읽고 판단할 수 있도록 배경을 포함했다.
> 작성: 2026-10-12 / 상태: **제안 (검토 대기)**

---

## 1. 배경

### 만들고 있는 것
금융·커머스 고객센터의 **전화 상담 AI 에이전트**의 「두뇌」 (STT·TTS는 범위 밖, 음성은 제약 조건으로만 고려).
- 인바운드: 소비자 문의·처리 업무 (배송, 반품, 착오송금, 카드 분실 등)
- 아웃바운드: 셀러·광고주에게 거는 안내·정보 수집 전화
- 지식: 공개 FAQ 1,250건 + 판매자 문서 65개 (하이브리드 검색 + 리랭크 구현 완료)
- 도구: 조회(주문·송금·카드·셀러), 링크 문자 발송, 직접 실행(카드 정지 등), 상담원 이관, 재통화 예약

### 제약
| 제약 | 내용 |
|---|---|
| **지연** | 실시간 전화. 첫 응답 시작이 늦으면 대화가 깨진다. 현재 로컬 LLM(27B)으로 짧은 답 생성에 3~4초, 첫 글자까지 약 2.8초 |
| **절차·규정** | 본인 확인 전 실행 금지, 실행 전 말로 재확인, 아웃바운드 고지 항목 누락 금지, 금액·결과 약속 금지 |
| **안전** | 사기·보이스피싱 신호, 오안내 위험, 긴 대화 → 사람 상담원 이관 |
| **확장** | 업무가 계속 늘어난다 (커머스·광고 → CX → 계열사 → 외부 고객사) |
| **평가** | 시나리오 기반 자동 평가(가짜 고객 + LLM 채점)로 개선 효과를 수치로 보여야 한다 |
| **자원** | GPU 1장(24GB), 로컬 LLM. LLM 호출 하나하나가 비싸다 |

### 시나리오 (요약)
| ID | 업무 | 성격 |
|---|---|---|
| S1 | 쇼핑 배송 문의 | 열린 질문 + 내 주문 조회 |
| S3 | 교환·반품 | 절차 있음 — 사유별 분기, 링크 안내 |
| S4 | 착오송금 | 분기 많음 — 지인/모르는 사람/사기/본인 계좌 |
| S5 | 카드 분실 | **강한 절차** — 인증 → 선택 → 재확인 → 실행 |
| S7 | 안심보상 서류 | 긴 안내 → 문자 발송, 사기면 이관 |
| O1 | 셀러 페널티 사전 안내 (아웃바운드) | **고정 단계** — 담당자 확인 → 고지 → 반발 대응 → 소명 안내 |
| O2 | 광고 1차 컨택 (아웃바운드) | 고정 단계 + 정보 수집(니즈·예산·관심도) |
| (후보) H1 | 「카드 잃어버렸는데 모르는 결제가 찍혔어요」 | **한 통화에 업무 2개** — 우선순위·전환 |
| (후보) H2 | 한도 문의처럼 보이는 보이스피싱 신호 | 겉 요청을 들어주지 말고 안전 조치로 전환 |

고객 행동 변형(모든 시나리오에 교차): 협조적 / 끼어들기·정정 / 정보 모호 / **주제 전환** / 침묵 / 감정 고조 / 범위 밖 요청 / 본인 확인 거부 / 상담원 요청

**특징**: 대부분의 통화는 **업무 1개**이고, 그 업무는 **정해진 절차**가 있다. 열린 질문은 일부. 한 통화에 여러 업무는 드물지만 중요하다.

## 2. 후보 구조

### A. ReAct 단일 에이전트
하나의 LLM이 모든 도구와 모든 업무 규칙을 프롬프트로 들고, 매 스텝 「도구 호출 / 답변」을 스스로 결정.

### B. 오케스트레이터-워커 (동적)
매 턴 오케스트레이터 LLM이 요청을 해석해 업무별 워커(전용 프롬프트·도구)에게 위임하고 결과를 종합. 필요하면 여러 워커를 계획·조합.

### C. 라우터 + 업무별 워커 (제안안)
```
매 턴
 ├─ 진행 중인 업무가 있음 → 해당 워커로 바로 (라우터 LLM 호출 없음)
 │     예외: 가드레일이 주제 전환·사기 신호·상담원 요청을 감지 → 라우터로
 └─ 진행 중인 업무 없음 → 라우터가 업무 판별 → 워커 배정

워커 = 업무별 상태 머신(단계·허용 도구를 코드로 강제) + 단계 안에서 짧은 ReAct(검색·조회·말하기)
일반 문의 워커 = 상태 머신 없이 ReAct만
```
- 라우터는 계획을 세우지 않고 **업무 판별·전환·우선순위**만 한다.
- 업무 전환 시 앞 업무 상태를 보관했다가 복귀한다.
- 이관 시 라우터가 통화 요약을 만들어 상담원에게 넘긴다.

### D. Plan-and-Execute (참고)
요청을 작업 DAG로 계획 → 실행 → 재계획. 분해 가능한 작업에 강하지만 **매 요청 계획 단계 = 추가 LLM 호출 + 지연**. 대화형 상담에는 맞지 않는다고 보고 후보에서 제외.

## 3. 비교

| 기준 | A. ReAct 단일 | B. 오케스트레이터-워커(동적) | C. 라우터 + 워커 |
|---|---|---|---|
| **턴당 LLM 호출** | 1~2 (도구 쓰면 +1) | 오케스트레이터 1 + 워커 1~2 (+종합 1) | 대부분 워커 1~2 (업무 시작·전환 턴만 라우터 +1) |
| **지연** | 가장 낮음 | 가장 높음 | A와 거의 같음 |
| **절차 강제** (인증 전 실행 금지 등) | 프롬프트 의존 — 건너뛸 수 있음 | 워커 프롬프트 의존 | **코드(상태 머신)로 강제** — 허용되지 않은 도구는 호출 자체가 불가 |
| **도구 혼동** | 도구가 늘수록 커짐 | 워커별로 좁힘 | 워커·단계별로 좁힘 |
| **업무 추가 비용** | 거대 프롬프트 수정 → 회귀 위험 | 워커 추가 + 오케스트레이터 수정 | **워커 추가 + 라우터에 업무 설명 1줄** |
| **평가·개선(APO)** | 실패 원인이 한 프롬프트에 섞임 | 워커별 가능, 오케스트레이터 오류가 섞임 | 업무·단계별로 분리 측정 가능 |
| **복합 업무 (H1)** | 한 루프에서 꼬이기 쉬움 | 강함 | 라우터가 우선순위·전환 관리 — 충분 |
| **주제 전환 (B3)** | 자연스럽지만 앞 업무 상태가 흐려짐 | 강함 | 가드레일 감지 → 라우터. 감지 실패 시 워커가 엉뚱하게 답할 위험 |
| **열린·예상 밖 질문** | 가장 유연 | 유연 | 일반 문의 워커로 처리 — 업무 판별 실패 시 어색할 수 있음 |
| **구현 복잡도** | 낮음 | 높음 | 중간 |

## 4. 제안: C (라우터 + 업무별 워커)

**근거**
1. 시나리오 대부분이 **정해진 절차의 처리 업무** → 절차를 코드로 강제하는 것이 안전성(인증·재확인·고지 누락)에 가장 직접적이다.
2. 전화 상담의 **지연 제약** → 매 턴 오케스트레이터를 거치는 B는 비용이 크다. C는 진행 중 업무에 바로 붙어 A 수준의 지연을 유지한다.
3. 업무가 계속 늘어나는 환경 → 워커 단위로 추가·평가·개선하는 구조가 지속 가능하다.
4. ReAct의 유연성은 버리지 않고 **워커 안(단계 내 행동)과 일반 문의 워커**에서 쓴다.

**검증 계획**
- 현재 구현된 A(단일 에이전트)를 **기준선**으로 남기고, C를 구현해 **같은 시나리오로 비교**한다.
- 지표: 시나리오 통과율, **절차 위반 건수**(인증 전 실행·재확인 누락·고지 누락), 근거 없는 발화 비율, 턴 지연(중앙값·p90), 턴당 LLM 호출 수, 주제 전환 시나리오 통과율.
- 판단 기준: C가 절차 위반을 의미 있게 줄이면서 지연 증가가 작으면 채택. 차이가 없으면 A를 유지하고 그 결과를 보고한다.

## 5. 내가 확신하지 못하는 부분 (검토 요청)

1. **라우터를 LLM으로 둘지, 분류기·규칙으로 둘지** — 업무 판별은 짧은 분류 문제라 소형 모델이나 규칙으로 충분할 수도 있다. 지연·정확도 균형은?
2. **주제 전환 감지를 누가 하나** — 워커가 매 턴 「이건 내 업무가 아니다」를 판단하게 할지, 별도 가드레일이 감지할지. 감지 실패 시의 비용이 가장 큰 약점이라고 본다.
3. **상태 머신의 경직성** — 고객이 단계를 건너뛰는 정보를 먼저 말하는 경우(예: 묻기 전에 「일시정지 말고 분실신고로 해주세요」) 상태 머신이 자연스럽게 처리할 수 있나. 슬롯 채우기 방식(순서 대신 필요한 정보가 다 모이면 진행)이 나을까?
4. **A를 강화하는 대안** — A에 「도구 실행 전 정책 검사(가드레일)」만 붙여도 절차 위반 대부분을 막을 수 있지 않나? 그렇다면 C의 복잡도가 정당화되나?
5. **아웃바운드(O1·O2)** — 고정 단계라 워커 하나의 상태 머신으로 충분하고 라우터가 거의 필요 없다고 봤는데, 맞나?
6. 업계 실무(음성 상담 에이전트 프레임워크·프로덕션 사례)에서 일반적인 선택은 무엇인가?

## 6. 결정이 바뀌는 조건

| 이런 결과가 나오면 | 결정 |
|---|---|
| A + 도구 실행 전 정책 검사만으로 절차 위반이 C와 비슷하게 줄어듦 | **A + 가드레일** 채택 (단순한 쪽) |
| 업무 판별·전환 오류가 잦아 C의 통과율이 A보다 낮음 | 라우터 개선 또는 A 유지 |
| 한 통화 다중 업무가 예상보다 흔함 | B 쪽으로 이동 검토 |
| C의 지연이 A 대비 크게 늘어남 (p90 +1초 이상) | 라우터를 소형 모델·규칙으로 교체 |
