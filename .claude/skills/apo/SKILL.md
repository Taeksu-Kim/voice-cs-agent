# apo — 지시문 수정 후보 만들기

입력: triage 케이스 폴더와 문제 번호 (`runs/cases/<시각>/<케이스> <issue 번호>`). 그 문제의 `layer`가 `prompt`여야 한다.

**저장소의 지시문(`csagent/agent/protocols/*.yaml`, `csagent/agent/prompts.py`)을 고치지 않는다.**
후보는 `scripts/apo_candidate.py`로 실험 폴더에 사본으로만 만든다. 최종 반영은 사람이 결정한다.

> 지금 범위: 후보 작성 · 원칙 점검 · 모순 검토 · 제안까지.
> 다음 단계: **apo-test 스킬**이 이 실험 폴더를 받아 테스트 케이스 생성 → 후보마다 추론(재현 기준·변형·퇴행·회귀) → 출력 검토 → 선택을 하고 제안을 갱신한다.
> 이 스킬의 제안 확신도는 「원칙 점검만 거침, 테스트 전」이다.

## 도구 쓰는 법

- 파일 보기는 Read, 검색은 Grep(없으면 `grep -n` 한 줄). 플러그인·MCP 도구는 쓰지 않는다
- **백그라운드 실행(run_in_background)·Monitor를 쓰지 않는다. 명령은 하나씩 끝까지 기다린다** (Bash timeout 600000) —
  비대화형 실행이라 알림을 기다리면 세션이 끝나고 이어진 세션에서는 권한이 풀린다. 재현은 로컬 벡터 DB를 하나만 열 수 있어 동시에 돌리면 실패한다
- 명령은 한 줄에 하나, `cd`·변수·`&&`·파이프 없이. 파일은 아래 스크립트로만 만든다:
  - `/home/ubuntu/miniconda3/envs/customer-service-agent/bin/python scripts/apo_candidate.py new <케이스 폴더> <issue 번호>` → 실험 폴더 경로
  - `… apo_candidate.py add <실험 폴더> <후보 이름> <프로토콜 이름>` + heredoc으로 **프로토콜 파일 전체** (원문을 그대로 두고 바꿀 부분만 고친 것)
  - `… apo_candidate.py note <실험 폴더> <후보 이름>` + heredoc으로 원칙 점검·모순 검토
  - `… apo_candidate.py proposal <실험 폴더>` + heredoc으로 최종 제안
- 후보는 `common`과 `steps[].say` 문구만 바꿀 수 있다 (단계·조건·도구가 바뀌면 스크립트가 거부 — 그건 코드 층). `prompts.py`의 공통 규칙(`SYSTEM`)을 바꿔야 한다고 판단되면 후보를 만들지 말고 제안에 그렇게 적는다

## 먼저 읽을 것

- `reference/principles.md` — **프롬프트 작성 원칙 (이 스킬의 규칙)**
- 케이스의 `triage.md` (그 문제의 근거·재현·판단 이유), `case.json`, 신호 좌표 턴의 `llm_calls.jsonl` 원문 — **모델이 실제로 받은 입력 전체**
- 대상 지시문 전체: `csagent/agent/prompts.py`의 `SYSTEM` + 대상 프로토콜 yaml 전체(머리 주석의 과거 실패·결정 포함)
- `git log -p -- <대상 yaml>` — 이 지시문이 어떤 실패 때문에 지금 모양이 됐는지

## 순서

1. **실험 폴더** — `apo_candidate.py new`
2. **근본 요구사항 정하기** — triage의 제안은 「무엇이 안 됐나」다. 그 케이스를 막는 규칙이 아니라,
   그 행동이 자연스럽게 나오게 하는 **이 업무의 상담원에게 원래 필요한 요구사항**이 무엇인지 한두 문장으로 쓴다 (원칙 3).
   이미 있는 지시가 그 요구사항을 땜질 형태로 담고 있으면(예: 「고객이 같은 말을 다시 하면 …」) 그 지시를 대체하는 쪽을 먼저 본다
3. **후보 2~3개** — 서로 다른 접근으로 (예: common의 요구사항으로 / 해당 단계 say에서 고려할 항목으로 / 기존 지시를 줄이고 재구성).
   각 후보는 바뀐 줄이 적을수록 좋다. 원칙 1~4·6으로 문장마다 다듬는다
4. **모순 검토** (원칙 5) — 후보마다 바뀐 문장을 `SYSTEM`·같은 파일의 `common`·모든 단계 `say`와 대조한다:
   충돌하는 지시, 같은 말을 두 번 하는 지시, 다른 단계에서 의도하지 않은 행동을 부를 지시. 발견하면 고치거나 그 후보를 버린다
5. **근거 남기기** — 후보마다 `note`: 근본 요구사항 · 원칙 1~8 점검 (문장 단위로 어떻게 맞췄나 — 원칙 3의 점검 질문 두 가지는 문장마다 답을 적는다)
   · **새로 생길 수 있는 실패**(원칙 7)와 **지운·바꾼 문장이 막던 과거 실패**(원칙 8) — 각각 apo-test가 볼 수 있게 「테스트에서 볼 것」 형태로 · 모순 검토 결과 · 이 후보가 다른 케이스·단계에 미칠 수 있는 영향
6. **제안** — `proposal`: 추천 후보와 이유, 후보 비교 표, diff, 테스트 단계에서 볼 것(재현 기준 `spec`·`baseline`, 퇴행을 볼 시나리오), 확신도(테스트 전)

## 하지 않는 것

- 저장소 지시문·코드를 고치지 않는다
- 케이스 하나를 통과시키는 문장(그 케이스의 말·상황을 그대로 옮긴 규칙)을 넣지 않는다 — 원칙 3
- 재현 기준(triage의 `spec`)을 바꾸지 않는다
- 지시문으로 고칠 수 없는 문제라고 판단되면(입력에 필요한 정보가 없다, 구조 탓이다) 후보를 억지로 만들지 않고 제안에 「triage 층 재검토」로 적는다
